# User Journey — Angular UI Bundles (No-code + Pro-code)

**Goal:** Define the end-to-end developer experience for two paths:
- **No-code path** — paved template (`sf template generate -t angularbasic`), Vite + Analog
- **Pro-code path** — bring your own Angular project (Angular CLI / Vue / Next / 11ty / anything), AI-assisted wiring

This doc is **HLD only** — flows, decision points, touchpoints. Skill content and CLAUDE.md authoring live in follow-up docs.

---

## Personas

| Persona | Starting state | Wants |
|---|---|---|
| **P1 — No-code** | No existing app, just an idea | Fastest paved start. Doesn't care about toolchain. |
| **P2 — Pro-code: greenfield** | No existing app, but has a strong toolchain preference (e.g., "I want Angular CLI / Vue / Next") | Builds the project their way; just wants the Salesforce wiring done correctly |
| **P3 — Pro-code: migration** | Existing Angular CLI / Vue / other app outside Salesforce | Bring the app into UI Bundles without rewriting |
| **P4 — Pro-code: experimenting** | Has played with UI Bundles via paved template; now wants to try a different stack | Wiring help for the new stack; doesn't want to lose what they've already built |

---

## Two Surfaces, One Outcome

The wiring (the 7 jobs the Vite plugin does today) lives in **one of three places** depending on the persona:

```
P1 (No-code)               →  Pre-built into the paved template (zero AI)
P2/P3/P4 (Pro-code)        →  Generated by AI skill into the user's project
```

The AI skill ships in **two surfaces** to meet developers where they are:

| Surface | Audience | Invocation |
|---|---|---|
| **Agentforce Vibes** | Salesforce-native users; web-based agentic IDE | User selects skill from catalog or `@`-mentions it |
| **Claude Code** (and other terminal IDE assistants) | Developers who use CLI / IDE assistants locally | Project-level skill + CLAUDE.md auto-loaded; invoked via slash command or natural language |

Both surfaces use the **same underlying skill logic** — different packaging.

## Journey 1 — No-code (P1)

**Trigger:** Developer wants to ship a Salesforce UI Bundle quickly. Doesn't have an existing app. Searches docs, finds the `sf` CLI command.

```
Discovery
   ↓
"sf template generate ui-bundle -n myApp -t angularbasic"
   ↓
Template generated in force-app/main/default/uiBundles/myApp/
   ↓
"npm install"  →  "npm run dev"  →  works at localhost
   ↓
"npm run build"  →  "sf project deploy start"
   ↓
App live on org
```

**Touchpoints:**
- Salesforce DX documentation page (links to template list)
- `sf template generate ui-bundle --help` (lists `angularbasic` alongside `reactbasic`)
- Generated `README.md` inside the template (next steps, architecture overview)

**Time-to-first-deploy:** ~10 minutes from `sf template generate` to deployed app.

**No AI surface involved.** The template ships with everything pre-wired.

**What user gets:**
- Working Vite + Analog Angular app
- All 7 platform jobs already wired via `@salesforce/vite-plugin-ui-bundle`
- Pre-filled Salesforce metadata (`.uibundle-meta.xml`, `ui-bundle.json`, `.forceignore`)
- Standard Angular component patterns, routing, forms ready to extend

**Exit ramps to pro-code:**
- User later decides they want Angular CLI workflow → see Journey 4 (experimenting)
- User wants to add a non-paved framework dep that breaks the Vite path → see Journey 2 / 3

## Journey 2 — Pro-code: Greenfield with Custom Toolchain (P2)

**Trigger:** Developer wants Angular on Salesforce **but specifically wants Angular CLI** (or Vue, Next, etc.). Searches docs, finds the pro-code path.

```
Discovery
   ↓
Pro-code docs say: "Use your toolchain, AI skill will wire it for Salesforce"
   ↓
User picks AI surface:
   ├──→ Agentforce Vibes  (web-based)
   └──→ Claude Code        (local, with our skill installed)
   ↓
User describes intent:
   "I want to build a new Angular CLI app as a Salesforce UI Bundle"
   ↓
AI skill asks clarifying questions:
   - Project name?
   - Org alias?
   - Which Angular version?
   - Karma or Jasmine for tests?
   ↓
AI skill generates:
   1. SFDX folder placement (force-app/main/default/uiBundles/<name>/)
   2. Bootstraps Angular CLI project (`ng new` invocation)
   3. Adds Salesforce metadata files (.uibundle-meta.xml, ui-bundle.json, .forceignore)
   4. Adds Salesforce npm deps (@salesforce/sdk-data, @salesforce/ui-bundle, @angular-builders/custom-esbuild)
   5. Creates custom-esbuild.config.ts wiring the 7 platform jobs
   6. Creates proxy.conf.js using createProxyHandler
   7. Wires APP_BASE_HREF in app.config.ts
   8. Updates angular.json to use custom-esbuild builder
   ↓
User reviews changes (diff in IDE / Vibes UI)
   ↓
User runs "ng serve" / "ng build"  →  deploys
   ↓
App live on org with full Salesforce platform features
```

**Touchpoints:**
- Pro-code docs page (entry point, explains what the skill does)
- AI skill catalog / discovery in Agentforce Vibes
- IDE / Claude Code experience for the local path
- Generated README explaining "what AI did to your project"

**Time-to-first-deploy:** ~30 minutes (longer than no-code because user installs deps, reviews generated files).

**Critical guardrails the AI skill must enforce:**
- The 7 jobs MUST be wired correctly (especially `__SF_API_VERSION__` substitution — silent failure otherwise)
- Generated files use the **same primitives** as the paved template (`@salesforce/ui-bundle/{app, proxy}`) — no custom proxy reimplementation
- Output is reviewable — no magic; user can read every generated file and understand it

**What user gets:**
- An Angular CLI project they can extend with `ng generate`, `ng update`, `ng add`
- All Salesforce platform features working
- Their preferred ng workflow preserved

## Journey 3 — Pro-code: Migration of Existing App (P3)

**Trigger:** Developer has an existing Angular CLI app (or Vue / Next / 11ty / whatever). Wants to deploy it as a Salesforce UI Bundle.

```
Discovery
   ↓
User finds pro-code docs / migration guide
   ↓
User picks AI surface:
   ├──→ Agentforce Vibes  (paste / link to repo, web-based)
   └──→ Claude Code        (in their existing repo, local)
   ↓
User describes intent:
   "I have an existing Angular CLI app at /path/to/myapp. Make it a Salesforce UI Bundle."
   ↓
AI skill analyzes the repo:
   - Detects framework (Angular / Vue / Next / Svelte / etc.)
   - Detects builder (`:application` / `:browser` / Vite / webpack / Next / etc.)
   - Detects Angular version
   - Detects test runner (Karma / Jest / Vitest)
   - Detects existing customizations (custom builders, special webpack config)
   ↓
AI skill generates a migration plan and shows it to the user:
   - "Move project into force-app/main/default/uiBundles/<name>/"
   - "Add metadata files (X, Y, Z)"
   - "Add deps (A, B, C)"
   - "Generate wiring file (D)"
   - "Modify <bundler config> to use the wiring"
   - "Wire APP_BASE_HREF (or framework equivalent)"
   ↓
User reviews plan  →  approves
   ↓
AI skill executes the plan, creates a single PR/diff
   ↓
User runs their existing build command (npm run build / ng build / next build)
   ↓
"sf project deploy start"
   ↓
App live on org, customer's existing tooling intact
```

**Touchpoints:**
- Migration guide doc (sets expectations: what we don't change, what we add)
- Detected-stack feedback before action (transparency: "We see you're on Angular 18, `:browser` builder, Karma tests")
- Generated diff for review
- Post-migration troubleshooting docs (FAQ for common edge cases)

**Time-to-first-deploy:** Hours, not days. Customer keeps their entire existing workflow; we add ~5 files.

**Critical guardrails the AI skill must enforce:**
- **Don't touch source code** — only add metadata + wiring config files
- **Don't change `package.json` scripts** unless absolutely required (preserve `ng serve`, `ng test`, etc.)
- **Don't migrate Angular versions** — if they're on `:browser` and need `:application`, surface that as a prerequisite, not auto-perform
- **Show a "what changed" report** so user understands the surface area we touched

**Edge cases the skill needs to handle:**
- Older Angular (v16 or earlier on `:browser`) → surface "you need to `ng update` first" message; don't try to do it automatically
- Nx workspaces / multi-project setups → ask which project to wire
- Custom webpack builders → flag potential conflicts before generating
- Already-deployed-elsewhere projects → ensure we don't conflict with their existing deploy pipelines

**What user gets:**
- Their existing app, untouched at the code level
- New Salesforce wiring in 5 files
- Familiar build commands still work
- App lives on org

## Journey 4 — Pro-code: Experimenting From Paved Template (P4)

**Trigger:** Developer started with the paved Vite + Analog template (Journey 1), now wants to switch to Angular CLI workflow OR add a Vue micro-frontend OR experiment with another stack.

```
User has working Vite + Analog template
   ↓
User decides: "I want Angular CLI workflow instead"
   OR: "I want to add a Vue page alongside Angular"
   OR: "Let me try this with Next.js"
   ↓
User invokes AI skill in their existing project:
   ├──→ Agentforce Vibes
   └──→ Claude Code
   ↓
User describes intent:
   "Convert this from Vite + Analog to Angular CLI"
   OR: "Add a Vue page at /vue-route"
   ↓
AI skill recognizes the existing UI Bundle structure
   AI skill performs the relevant operation:
   - For "convert to CLI": generates Journey 3-style migration in reverse
   - For "add Vue page": generates a sub-project with its own wiring
   ↓
User reviews diff  →  approves
   ↓
Continue dev with new toolchain
```

**Touchpoints:**
- "Switch toolchain" guide (sets expectations: this is a one-way migration)
- Examples / demos of common conversions
- Honest warnings about cost (e.g., "Switching from Vite + Analog to Angular CLI takes ~1 day for a small app")

**Time-to-completion:** Hours to days depending on app size.

**Critical guardrails:**
- **Confirm intent** — switching toolchains is rare and irreversible-ish; user should explicitly opt in
- **Backup / git checkpoint** before generating large diffs
- **Estimate effort upfront** so user can decline if it's too costly

**What user gets:**
- A converted project on the new toolchain
- All Salesforce platform features still working
- Git history preserved

## AI Surface Details

### Agentforce Vibes

| Aspect | Detail |
|---|---|
| **Discovery** | Skill listed in Agentforce Vibes catalog under "UI Bundles" or "Salesforce Platform" |
| **Invocation** | User opens Vibes, types intent; skill is suggested. Or user `@`-mentions skill name. |
| **Inputs needed** | Project context (file tree, package.json), user intent |
| **Outputs** | Generated files, diff preview, plan-to-execute approval flow |
| **Where files live** | User's connected workspace / scratch org / managed dev environment |
| **Auth context** | User's `sf` session is already known |

### Claude Code (and other terminal IDE assistants)

| Aspect | Detail |
|---|---|
| **Discovery** | Project-level CLAUDE.md auto-loaded on `cd <project>`. User-level skill installed via plugin marketplace. |
| **Invocation** | Slash command (`/ui-bundle-init`, `/ui-bundle-migrate`) OR natural language ("Make this an Angular Salesforce UI Bundle") |
| **Inputs needed** | Project files (read), user intent |
| **Outputs** | File diffs (Edit / Write tool calls), plan in conversation, command suggestions |
| **Where files live** | Local filesystem |
| **Auth context** | Local `sf` CLI session |

### Other surfaces (future)

- VS Code Live Preview extension (built-in tip / link to skill)
- `sf` CLI itself (`sf ui-bundle wire --framework=angular-cli` shells out to the skill or its underlying logic)
- GitHub Copilot / Cursor / Codeium — if we package the skill as a generic instruction set, any AI assistant can invoke it

|---|---|---|

| **AI surface** | Agentforce Vibes vs Claude Code vs other | Agentforce Vibes (Salesforce-native) |

## Risks / Open Questions

1. **AI skill quality bar** — generated wiring must be production-grade, not "demoware." Misconfigured wiring (e.g., wrong API version) silently fails. Validation / golden-tests needed for the skill output.

2. **Stack detection accuracy** — for migration journeys, the skill must correctly detect the customer's framework / builder / version. Misdetection → wrong wiring. May need fallback "tell me what you have" prompts.

3. **AI surface parity** — same skill logic must produce same output in Agentforce Vibes vs Claude Code. Otherwise customers get inconsistent advice depending on tool.

4. **Discoverability** — pro-code path needs to be obvious to customers. If they only see "use the template," they won't know AI-assisted wiring exists.

5. **Versioning** — when `@salesforce/ui-bundle` primitives change, the AI skill needs to know. Skill prompt / instruction set needs to be versioned alongside the package.

6. **Failure modes for older Angular** — for customers on `:browser` builder or pre-v17 Angular, the skill should detect this and give clear "upgrade Angular first" guidance, not try to wire a non-functional setup.

7. **Test coverage of wiring** — for each generated config, do we have an automated test that proves it produces a working app on a representative project?

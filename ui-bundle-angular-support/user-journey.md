# User Journey — UI Bundles (No-code + Pro-code)

**Goal:** Define the end-to-end developer experience for two paths:
- **No-code path** — paved templates (`sf template generate -t <framework>basic`), each built on Vite + the framework's Vite plugin. Today: `reactbasic`. Next: `angularbasic` (Vite + Analog). Future: Vue, Svelte, Lit, etc.
- **Pro-code path** — bring your own UI project (Angular CLI, Vue, Next, Svelte/SvelteKit, 11ty, Astro, anything), AI-assisted wiring

This doc is **HLD only** — flows, decision points, touchpoints. Skill content and CLAUDE.md authoring live in follow-up docs.

---

## Personas

| Persona | Starting state | Wants |
|---|---|---|
| **P1 — No-code** | No existing app, just an idea | Fastest paved start. Doesn't care about toolchain. |
| **P2 — Pro-code: greenfield** | No existing app, but has a strong toolchain preference (e.g., "I want Angular CLI" / "I want Next.js" / "I want SvelteKit") | Builds the project their way; just wants the Salesforce wiring done correctly |
| **P3 — Pro-code: migration** | Existing app outside Salesforce (any framework, any toolchain) | Bring the app into UI Bundles without rewriting |

---

## Two Surfaces, One Outcome

The Salesforce wiring (proxy support, environment / `SFDC_ENV` injection, manifest loading, API version substitution, dev server config, design instrumentation) lives in **one of two places** depending on the persona:

```
P1 (No-code)               →  Pre-built into the paved template (zero AI)
P2/P3 (Pro-code)           →  Generated by AI skill into the user's project
```

The AI skill ships in **two surfaces** to meet developers where they are:

| Surface | Audience | Invocation |
|---|---|---|
| **Agentforce Vibes** | Salesforce-native users; web-based agentic IDE | User selects skill from catalog or `@`-mentions it |
| **Claude Code** (and other terminal IDE assistants) | Developers who use CLI / IDE assistants locally | Project-level skill + CLAUDE.md auto-loaded; invoked via slash command or natural language |

Both surfaces use the **same underlying skill logic** — different packaging.

## Journey 1 — No-code (P1)

**Trigger:** Developer wants to ship a Salesforce UI Bundle quickly. Doesn't have an existing app. Searches docs, finds the `sf` CLI command.

```
Discovery
   ↓
"sf template generate ui-bundle -n myApp -t <framework>basic"
   (e.g., -t reactbasic | -t angularbasic | -t vuebasic in future)
   ↓
Template generated in force-app/main/default/uiBundles/myApp/
   ↓
"npm install"  →  "npm run dev"  →  works at localhost
   ↓
"npm run build"  →  "sf project deploy start"
   ↓
App live on org
```

**Touchpoints:**
- Salesforce DX documentation page (links to template list)
- `sf template generate ui-bundle --help` (lists all available `<framework>basic` templates)
- Generated `README.md` inside the template (next steps, architecture overview)

**No AI surface involved.** The template ships with everything pre-wired.

**What user gets:**
- Working app on **Vite + the framework's Vite plugin** (e.g., `@vitejs/plugin-react` for React, `@analogjs/vite-plugin-angular` for Angular, etc.)
- Salesforce platform wiring already done via `@salesforce/vite-plugin-ui-bundle` — proxy, environment injection, manifest, API version substitution, design instrumentation
- Pre-filled Salesforce metadata (`.uibundle-meta.xml`, `ui-bundle.json`, `.forceignore`)
- Framework-idiomatic component patterns, routing, forms ready to extend

## Journey 2 — Pro-code: Greenfield with Custom Toolchain (P2)

**Trigger:** Developer wants to build on Salesforce but **specifically wants their preferred CLI / framework** (e.g., "I want Angular CLI" / "I want Next.js" / "I want SvelteKit" / "I want plain Vite + Vue"). Searches docs, finds the pro-code path.

```
Discovery
   ↓
Pro-code docs say: "Use your toolchain, AI skill will wire it for Salesforce"
   ↓
User picks AI surface:
   ├──→ Agentforce Vibes  (web-based)
   └──→ Claude Code        (local, with our skill installed)
   ↓
User describes intent (examples):
   "I want to build a new Angular CLI app as a Salesforce UI Bundle"
   "I want to start a Next.js project as a UI Bundle"
   "I want to use SvelteKit"
   ↓
AI skill asks clarifying questions specific to the chosen stack:
   - Project name?
   - Org alias?
   - Stack-specific config (e.g., for Angular CLI: which version? Karma or Jasmine?
     for Next.js: app router or pages? for SvelteKit: adapter?)
   ↓
AI skill generates:
   - SFDX folder placement (force-app/main/default/uiBundles/<name>/)
   - Bootstraps the project using the user's chosen tool (`ng new`, `npx create-next-app`,
     `npm create svelte`, etc.)
   - Salesforce metadata files (.uibundle-meta.xml, ui-bundle.json, .forceignore)
   - Salesforce npm deps (@salesforce/sdk-data, @salesforce/ui-bundle, plus stack-specific
     build-tool customization deps)
   - Build-tool wiring file appropriate to the stack — covering proxy support, environment
     injection, manifest loading, API version substitution
   - Proxy config file using createProxyHandler from @salesforce/ui-bundle/proxy
   - Base-path / router wiring in the framework's idiomatic location
   - Bundler config updates so the wiring is loaded
   ↓
User reviews changes (diff in IDE / Vibes UI)
   ↓
User runs their stack's build/serve commands  →  deploys
   ↓
App live on org with full Salesforce platform features
```

**Touchpoints:**
- Pro-code docs page (entry point, explains what the skill does)
- AI skill catalog / discovery in Agentforce Vibes
- IDE / Claude Code experience for the local path
- Generated README explaining "what AI did to your project"

**Critical guardrails the AI skill must enforce:**
- All wiring (proxy, environment injection, API version substitution) must be correct — especially API version substitution, which silently fails if missed
- Generated files use the **same primitives** as the paved template (`@salesforce/ui-bundle/{app, proxy}`) — no custom proxy reimplementation
- Output is reviewable — no magic; user can read every generated file and understand it

**What user gets:**
- A project on **their chosen toolchain**, fully extensible with that toolchain's standard commands (`ng generate`, `next dev`, `svelte-kit`, etc.)
- All Salesforce platform features working
- Their preferred workflow preserved

## Journey 3 — Pro-code: Migration of Existing App (P3)

**Trigger:** Developer has an existing app (any framework — Angular CLI / React / Vue / Next / SvelteKit / 11ty / Astro / etc.). Wants to deploy it as a Salesforce UI Bundle.

```
Discovery
   ↓
User finds pro-code docs / migration guide
   ↓
User picks AI surface:
   ├──→ Agentforce Vibes  (paste / link to repo, web-based)
   └──→ Claude Code        (in their existing repo, local)
   ↓
User describes intent (examples):
   "I have an existing Angular CLI app at /path/to/myapp. Make it a Salesforce UI Bundle."
   "I have a Next.js app, add Salesforce platform support."
   ↓
AI skill analyzes the repo:
   - Detects framework (React / Angular / Vue / Next / Svelte / etc.)
   - Detects builder (Angular CLI :application / :browser / Vite / webpack / Next / etc.)
   - Detects framework version
   - Detects test runner (Karma / Jest / Vitest / Playwright)
   - Detects existing customizations (custom builders, special bundler config)
   ↓
AI skill generates a migration plan and shows it to the user:
   - "Move project into force-app/main/default/uiBundles/<name>/"
   - "Add metadata files"
   - "Add Salesforce npm deps"
   - "Generate wiring file (covers proxy, env injection, manifest, API version)"
   - "Modify <bundler config> to use the wiring"
   - "Wire base path / router (framework-idiomatic location)"
   ↓
User reviews plan  →  approves
   ↓
AI skill executes the plan, creates a single PR/diff
   ↓
User runs their existing build command (npm run build / ng build / next build / vite build / etc.)
   ↓
"sf project deploy start"
   ↓
App live on org, customer's existing tooling intact
```

**Touchpoints:**
- Migration guide doc (sets expectations: what we don't change, what we add)
- Detected-stack feedback before action (transparency: "We see you're on Next.js 14 / Angular 18 :application / Vite + Vue 3 / etc.")
- Generated diff for review
- Post-migration troubleshooting docs (FAQ for common edge cases)

**Critical guardrails the AI skill must enforce:**
- **Don't touch source code** — only add metadata + wiring config files
- **Don't change `package.json` scripts** unless absolutely required (preserve their existing dev/test/build commands)
- **Don't migrate framework versions** — if their version needs an upgrade for our wiring to work, surface that as a prerequisite, not auto-perform
- **Show a "what changed" report** so user understands the surface area we touched

**Edge cases the skill needs to handle:**
- Older framework versions (e.g., older Angular CLI on `:browser` builder, very old Next.js, etc.) → surface "you may need to upgrade your framework first" message; don't try to do it automatically
- Monorepo / multi-project setups (Nx, Turborepo, npm workspaces) → ask which project to wire
- Custom build configurations (custom webpack, custom Vite plugins) → flag potential conflicts before generating

**What user gets:**
- Their existing app, untouched at the code level
- New Salesforce wiring added in a small set of new files
- Familiar build commands still work
- App lives on org

## AI Surface Details

### Agentforce Vibes

| Aspect | Detail |
|---|---|
| **Discovery** | Skill listed in Agentforce Vibes catalog under "UI Bundles" or "Salesforce Platform" |
| **Invocation** | User opens Vibes, types intent; skill is suggested. Or user `@`-mentions skill name. |
| **Inputs needed** | Project context (file tree, package.json), user intent |
| **Outputs** | Generated files, diff preview, plan-to-execute approval flow |
| **Where files live** | User's connected workspace / scratch org / managed dev environment |
| **Auth context** | User's `sf` session is already known |

### Claude Code (and other terminal IDE assistants)

| Aspect | Detail |
|---|---|
| **Discovery** | Project-level CLAUDE.md auto-loaded on `cd <project>`. User-level skill installed via plugin marketplace. |
| **Invocation** | Slash command (`/ui-bundle-init`, `/ui-bundle-migrate`) OR natural language ("Make this a Salesforce UI Bundle") |
| **Inputs needed** | Project files (read), user intent |
| **Outputs** | File diffs (Edit / Write tool calls), plan in conversation, command suggestions |
| **Where files live** | Local filesystem |
| **Auth context** | Local `sf` CLI session |

### Other surfaces (future)

- VS Code Live Preview extension (built-in tip / link to skill)
- `sf` CLI itself (`sf ui-bundle wire --framework=<framework>` shells out to the skill or its underlying logic)
- GitHub Copilot / Cursor / Codeium — if we package the skill as a generic instruction set, any AI assistant can invoke it

## Decision Points (where user makes a choice)

| Decision point | What the customer is choosing | Default |
|---|---|---|
| **Paved vs pro-code** | Speed vs control | Paved (recommended for new projects) |
| **AI surface** | Agentforce Vibes vs Claude Code vs other | Agentforce Vibes (Salesforce-native) |
| **Framework / toolchain** | React / Angular / Vue / Next / Svelte / etc. with the user's preferred CLI | Their existing tooling, if any |
| **Action scope** | Greenfield vs migration | Detected from project state |

## What Success Looks Like

| Persona | Success metric |
|---|---|
| P1 (No-code) | Generates template, runs through dev → build → deploy without touching wiring code |
| P2 (Pro-code greenfield) | Their preferred toolchain commands all work; Salesforce wiring is correct on first run |
| P3 (Pro-code migration) | Existing source code untouched; app deploys with their existing build commands |

**Across all personas:**
- User reads what AI generated and understands it
- User can re-run the skill safely (idempotent)
- Failures surface clearly with actionable next steps

## Risks / Open Questions

1. **AI skill quality bar** — generated wiring must be production-grade, not "demoware." Misconfigured wiring (e.g., wrong API version) silently fails. Validation / golden-tests needed for the skill output.

2. **Stack detection accuracy** — for migration journeys, the skill must correctly detect the customer's framework / builder / version. Misdetection → wrong wiring. May need fallback "tell me what you have" prompts.

3. **AI surface parity** — same skill logic must produce same output in Agentforce Vibes vs Claude Code. Otherwise customers get inconsistent advice depending on tool.

4. **Discoverability** — pro-code path needs to be obvious to customers. If they only see "use the template," they won't know AI-assisted wiring exists.

5. **Versioning** — when `@salesforce/ui-bundle` primitives change, the AI skill needs to know. Skill prompt / instruction set needs to be versioned alongside the package.

6. **Failure modes for older framework versions** — for customers on outdated frameworks (e.g., older Angular CLI builders, old Next.js), the skill should detect this and give clear "upgrade your framework first" guidance, not try to wire a non-functional setup.

7. **Test coverage of wiring** — for each generated config, do we have an automated test that proves it produces a working app on a representative project?

| Phase | Deliverables |
|---|---|
